| :--- | :--- | :---: |

## 3. 修復前問題分析

1. **程式印出結果後無法結束**：`proxy1_thread`、`proxy2_thread` 為無窮迴圈且未設定 `daemon=True`。
2. **重傳流程整條不通**：
   - 第 242、247 行 `server_receive_thread` 被註解，Server 收不到 `REQUEST_RETRANSMISSION`。
   - Client 送出的重傳編號是 `client_last_sent_packet // 10`（**批次序號**），Server 卻當成**封包編號**處理。
   - Server 重傳的訊息以 `(重傳)` 結尾，Client 以 `int(received_data.split()[-1])` 解析時拋出 `ValueError`，接收迴圈被 `except Exception` 中斷。
3. **缺包判斷的預期編號固定 `+10`**（第 182 行）：
   - 單筆模式下每一筆封包都被誤判為缺包。
   - 批次模式下只要遺失一批，預期編號就永久錯位，後續每一批都被誤判為缺包。
4. **單筆模式缺少 Path 3**（第 56–68 行）：`server_send_single_data()` 未處理 `choice == "3"`，不會傳送任何封包，最後除以零崩潰。
5. **掉包統計單位不一致**：批次模式下 Proxy1 每丟棄一批（10 筆封包）只讓 `loss_buffer` 加 1，與單筆模式的單位不同，掉包率無法比較。
6. **路徑選擇次數只在批次 Path 3 統計**：其他組合一律顯示 `0 / 0`。
7. **比率計算未處理分母為 0**、**`stop_threads` 用法錯誤**（與 Q3 相同）。

## 4. 修復內容

### 4.1 重傳流程重新設計

```text
Client 收到封包 ──> 以 regex 解析訊息中所有封包編號（單筆、批次、重傳訊息皆適用）
   │
   ├─ 第一個編號 > 預期編號 ──> 中間有缺口 ──> REQUEST_RETRANSMISSION <起> <訖>
   │
   └─ 接收逾時 ──> 與 1 ~ num_packet 比對，仍有缺包（例如最後一批被丟棄）──> 要求重傳後繼續等待
                   連續 3 輪逾時都沒有收到新封包才放棄

Server 收到 REQUEST_RETRANSMISSION <起> <訖>
   └─ 只重傳已送出過的範圍，每筆標註 (重傳)，直接送回 Client（不經過會掉包的 Proxy）
```

### 4.2 修改清單

| 修改 | 對應問題 |
| :--- | :---: |
| Proxy、Server 接收端與傳送端執行緒設為 `daemon=True` | 1 |
| 啟用 `server_receive_thread`；重傳要求改為 `REQUEST_RETRANSMISSION <起始編號> <結束編號>`，連續缺包合併成區間 | 2 |
| 新增 `parse_packet_numbers()`，以 `re.findall(r"server (\d+)")` 解析編號，可處理 `(重傳)` 標記 | 2 |
| Client 改用「下一個預期編號 + 已收到編號集合」判斷缺口，不再假設固定步進 `+10` | 3 |
| 抽出 `choose_proxy()`，單筆與批次模式共用 Path 3 的分流規則 | 4 |
| Proxy1 / Proxy2 改以**封包數**統計遺失與延遲，另外記錄被丟棄 / 延遲的傳送次數 | 5 |
| 所有路徑與模式都統計 Path 1 / Path 2 的使用次數 | 6 |
| 新增 `safe_percent()`；移除 `stop_threads`，接收迴圈改以逾時結束 | 7 |
| 新增輸出：重傳要求次數、重傳補回封包、最終收到封包、最終缺少封包 | 可觀察性 |
| 支援命令列參數（見第 1 節），可調整 Path 3 比例與分流方式、封包數、批次大小、傳送間隔，並檢查無效輸入 | 測試便利性 |
| `BUFFER_SIZE` 由 `8192` 提高到 `65535`，可接收最大 UDP 封包（原設定只能容納約 350 筆一批） | 大批次傳輸 |
| Server 傳送失敗（例如超過 UDP 大小上限）時記錄並繼續，該段封包由 Client 之後要求重傳 | 大批次傳輸 |
| 新增輸出：要求重傳封包、重複收到封包、單次傳送最大位元組、傳送失敗次數、接收緩衝區大小 | 可觀察性 |
| 新增 `--rcvbuf` 參數，可加大 Proxy 與 Client 的 socket 接收緩衝區（`SO_RCVBUF`） | 大批次傳輸 |
| 新增輸出：傳送失敗封包，用來區分「Server 送不出去」與「作業系統在接收端丟棄」 | 可觀察性 |

### 4.3 統計欄位定義

| 欄位 | 定義 |
| :--- | :--- |
| 掉包率 | Proxy1 丟棄的封包數 ÷ 總封包數 × 100 |
| 封包延遲率 | Proxy2 延遲的封包數 ÷ 首次傳送就收到的封包數 × 100 |
| 封包接收（首次傳送） | 不含重傳，第一次傳送就送達 Client 的封包數 |
| 最終收到封包 | 包含重傳補回，Client 收到的不重複封包數 |
| 要求重傳封包 | Client 在重傳要求中列出的封包總數（同一筆可能被要求多次） |
| 重複收到封包 | Client 收到已經有的封包數（晚到的原封包，或多餘的重傳） |

## 7. 多情境實驗：路線與分流比例

以 `run_experiments.py` 自動執行 20 個情境 × 5 次 = 100 次（50 筆封包、批次 10 筆），結果存於 `results/`：

- [`results/summary.md`](./results/summary.md)：各情境平均值
- `results/raw_results.csv`：每次執行的原始數據

```bash
python run_experiments.py      # 每個情境重複 5 次，約 9 分鐘
python run_experiments.py 20   # 指定重複次數
```

| 群組 | 情境 | 目的 |
| :--- | :--- | :--- |
| **A 單一路徑** | Path 1、Path 2 × 單筆 / 批次 | 基準 |
| **B 前後段分流 (seq)** | Proxy1 比例 0、0.3、0.5、0.7、1.0 × 單筆 / 批次 | 比例對掉包與重傳的影響 |
| **C 隨機分流 (random)** | Proxy1 比例 0.3、0.5、0.7 × 單筆 / 批次 | 兩條路交錯使用時的影響 |

**100 次執行全部正常結束，且每次都收齊 50 / 50 筆。**

### 7.1 掉包率大致與走 Proxy1 的比例成正比（單筆模式）

| Proxy1 比例 | 0 | 0.3 | 0.5 | 0.7 | 1.0 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| 理論掉包率（比例 × 30%） | 0% | 9% | 15% | 21% | 30% |
| seq 實測平均 | 0.0% | 7.2% | 13.6% | 20.8% | 26.0% |
| random 實測平均 | — | 6.8% | 17.6% | 21.2% | — |

### 7.2 批次比單筆快，但數值波動大

- 批次約 `2.5s`、單筆約 `7.5s`；重傳要求次數從約 10 次降到約 1 次。
- 50 筆只分 5 批，**一批被丟就是 10 筆（掉包率一次跳 20%）**，5 次平均仍不穩定（例如 seq 0.7 為 16%，低於 seq 0.5 的 24%），需要更多重複次數才能比較。
- 最後一批被丟時需等待 2 秒逾時才會發現，因此有掉包的批次情境約 `3.2s`，沒有掉包的約 `2.45s`。

### 7.3 隨機分流會把「晚到」誤判成「遺失」

| 情境（單筆） | 實際遺失 | 要求重傳 | 多要求的 | 重複收到 |
| :--- | :---: | :---: | :---: | :---: |
| seq 0.3 / 0.5 / 0.7 | 3.6 / 6.8 / 10.4 | 3.6 / 6.8 / 10.4 | 0 | **0** |
| random 0.3 | 3.4 | 5.6 | 2.2 | **2.2** |
| random 0.5 | 8.8 | 10.2 | 1.4 | **1.4** |
| random 0.7 | 10.6 | 12.8 | 2.2 | **2.2** |

「多要求的」恰好等於「重複收到」：某筆封包走 Proxy2 被延遲 0.5 秒時，下一筆走 Proxy1 先到，Client 看到編號跳號就要求重傳，原封包稍後仍然送達而重複收到。seq 模式兩條路不交錯，所以不會發生。這是多路徑傳輸常見的**亂序問題**；TCP 以「收到 3 個重複 ACK 才判定遺失」來避免這種誤判。

## 8. 十萬筆封包：批次大小測試

目標：找出傳完 100,000 筆封包最快的批次大小。

```bash
python Q4.py 2 2 --packets=100000 --group=2800
```

- 測試批次：250、500、1000、2000、2500、2800，加上 UDP 上限附近的 2977、2978、3000
- Path 2（不模擬掉包）各 1 次、Path 1（30% 掉包）各 2 次，共 27 次
- 原始數據：`results/batch_size_sweep_100k.csv`

**27 次執行全部正常結束，且每次都收齊 100,000 筆。**

### 8.1 耗時結果

理論最短耗時 = 傳送次數 × `0.1s` + 結尾的 `2s` 接收逾時（Client 需等待 2 秒沒有新封包才確認結束）。

| 每批筆數 | 單次 bytes | 傳送次數 | 理論最短 | Path 2 耗時 | Path 1 耗時（2 次） | 傳送失敗 |
| :---: | ---: | :---: | ---: | ---: | ---: | :---: |
| 250 | 5,501 | 400 | 42.0 s | 45.7 s | 45.7 / 47.6 s | 0 |
| 500 | 11,001 | 200 | 22.0 s | 24.3 s | 23.8 / 25.7 s | 0 |
| 1000 | 22,001 | 100 | 12.0 s | 12.8 s | 12.9 / 12.9 s | 0 |
| 2000 | 44,001 | 50 | 7.0 s | 9.9 s | 9.5 / 9.3 s | 0 |
| 2500 | 55,001 | 40 | 6.0 s | 8.4 s | 8.4 / 13.0 s | 0 |
| **2800** | 61,600 | 36 | 5.6 s | **6.2 s** | 10.2 / 8.0 s | 0 |
| **2977** | 65,494 | 34 | 5.4 s | 7.8 s | **7.8 / 7.6 s** | 0 |
| 2978 | 65,516 | 34 | — | 24.1 s | 30.8 / 33.3 s | **29** |
| 3000 | 66,000 | 34 | — | 22.5 s | 33.8 / 33.3 s | **29** |

### 8.2 單次傳送上限：2,977 筆

- 編號 1 ~ 99,999 的封包每筆 22 bytes（`"Hi, I am server 12345\n"`），UDP 單一封包最多 **65,507 bytes**，因此上限為 `65507 ÷ 22 ≈ 2977` 筆。
- **2,978 筆以上**：Server 送出時直接失敗（34 次中 29 次），這些封包只能靠重傳補回。重傳一筆送一次，需要數萬次傳送，反而要 **22 ~ 34 秒**，比 1,000 筆一批還慢。

### 8.3 批次越大，越容易被作業系統掉包

Path 2 本身不模擬掉包，但 1,000 筆以上仍然出現重傳：

| 每批筆數 | Path 2 重傳要求次數 | Path 2 重傳補回封包 | 相當於被作業系統丟掉的批數 |
| :---: | ---: | ---: | :---: |
| 250 / 500 | 0 | 0 | 0 |
| 1000 | 3 | 3,000 | 3 |
| 2000 | 208 | 14,000 | 7 |
| 2500 | 1,091 | 7,500 | 3 |
| 2800 | 0 | 0 | 0 |
| 2977 | 1,609 | 17,862 | 6 |

Path 1 也有相同現象：例如 2800 第 1 次 Proxy1 丟了 39,200 筆，重傳卻補回 44,800 筆，多出的 5,600 筆（2 批）是作業系統丟的。

**原因**（已由 8.4 的實測證實）：Proxy2 延遲 0.5 秒時不會讀取 socket，期間 Server 又送來約 5 批，全部堆在 Proxy2 的接收緩衝區（Windows 預設 **65,536 bytes**）；批次一大，緩衝區就裝不下，作業系統直接丟棄後來的封包。之後重傳一筆一筆大量送出，也會塞滿 Client 的接收緩衝區，造成「要求重傳封包」大於「重傳補回封包」。2800 那次 Path 2 剛好沒有遇到延遲，所以完全沒有重傳。

在預設緩衝區下，每批 **500 筆以內**是唯一在兩條路徑的每次測試都沒有被作業系統掉包的設定：Proxy2 延遲時排隊約 5 批 × 11 KB ≈ 55 KB，仍在 64 KB 以內；每批 1,000 筆則約 110 KB，超過容量。

### 8.4 加大接收緩衝區（`--rcvbuf`）

以十萬筆封包，比較預設 64 KB 與 1 MB 接收緩衝區，每種各 3 次，共 30 次。原始數據：`results/rcvbuf_test_100k.csv`。「作業系統掉包」為「重傳補回封包 − Proxy1 實際丟棄封包」。

| 路徑 / 每批筆數 | 指標 | 64 KB（預設），3 次 | 1 MB，3 次 |
| :--- | :--- | :--- | :--- |
| Path 2 / 1000 | 作業系統掉包 | 11,000 / 1,000 / 2,000 | **0 / 0 / 0** |
| Path 2 / 2000 | 作業系統掉包 | 12,000 / 22,000 / 0 | **0 / 0 / 0** |
| Path 2 / 2977 | 作業系統掉包 | 23,816 / 11,908 / 8,931 | **0 / 0 / 0** |
| Path 2 / 2977 | 耗時 | 9.9 / 7.7 / 7.7 s | **6.1 / 5.8 / 5.6 s**（理論最短 5.4 s） |
| Path 1 / 2500 | 重傳要求次數 | 2,611 / 137 / 468 | **7 / 12 / 6** |
| Path 1 / 2977 | 重傳要求次數 | 836 / 7 / 992 | **8 / 5 / 9** |

- **1 MB 緩衝區完全消除了 Path 2 的作業系統掉包**，最大批次 2,977 筆也能穩定傳完，耗時接近理論最短值。
- Path 1 的「作業系統掉包」兩者都是 0，但 64 KB 時重傳要求多了上百倍：被作業系統丟掉的是**重傳封包本身**，只能一再重新要求，1 MB 後這個現象也消失了。
- 30 次全部正常結束，且每次都收齊 100,000 筆。

### 8.5 接收緩衝區的上限

以 `rcvbuf_capacity.py` 實測：接收端完全不讀取，持續送入最大批次（65,494 bytes），看實際能堆積多少。原始數據：`results/rcvbuf_capacity.csv`。

| `SO_RCVBUF` 設定 | 實際堆積的最大批次數 | 實際堆積量 |
| ---: | ---: | ---: |
| 65,536（預設） | **2** | 0.1 MB |
| 1,048,576（1 MB） | 17 | 1.1 MB |
| 16 MB | 257 | 16.1 MB |
| 64 MB | 1,025 | 64.0 MB |
| 256 MB | 4,099 | 256.0 MB |
| 1 GB | 16,395 | 1,024.0 MB |
| 2,147,483,647（約 2 GB） | 32,790 | 2,048.1 MB |

- Windows 接受的設定值上限為 **2,147,483,647 bytes（32 位元有號整數上限，約 2 GB）**，而且實測確實能堆積到設定的容量（另外可多容納 1 個封包）。實際可用量仍受電腦記憶體限制。
- **預設 64 KB 只能容納 2 個最大批次**，所以 Proxy2 延遲時排隊的約 5 批必定裝不下。

#### 緩衝區能搭配多大的批次？

**批次大小的上限不會因為緩衝區變大而提高**：一批最多 2,977 筆是 UDP 單一封包 65,507 bytes 的限制。緩衝區決定的是**能排隊幾批**：

| 情境 | 需要排隊的量 | 所需緩衝區 |
| :--- | :--- | :--- |
| Proxy2 延遲 0.5 秒，每 0.1 秒送 1 批 | 約 5 ~ 6 批 × 65,494 bytes | 約 **400 KB** |
| Proxy1 丟掉一整批後，重傳一次湧入 2,977 個小封包 | 約 2,977 × 30 bytes | 約 **90 KB** |

因此 **512 KB ~ 1 MB** 就足以搭配最大批次 2,977 筆；設到 GB 等級並不會更快，只會占用更多記憶體。若要讓一批超過 2,977 筆，必須在程式內把一批拆成多個 UDP 封包、在接收端重組，等於自行實作分段。

### 8.6 以 1 MB 緩衝區重跑批次大小測試

8.1 的結果混入了作業系統掉包的影響，因此以 `--rcvbuf=1048576` 重跑：Path 2、Path 1 × 9 種批次，上限內每種 3 次、超過上限每種 1 次，共 46 次。

```bash
python run_batch_sweep.py --repeats=3 --rcvbuf=1048576   # 約 12 分鐘
python run_batch_sweep.py --rcvbuf=0                      # 使用作業系統預設緩衝區
```

原始數據與平均值：`results/batch_size_sweep_100k_rcvbuf1m.csv`、[`results/batch_size_sweep_100k_rcvbuf1m.md`](./results/batch_size_sweep_100k_rcvbuf1m.md)

| :---: | ---: | :--- | ---: | :--- | ---: |
| 250 | 42.0 s | 45.7 s（45.7 / 45.8） | 45.7 s | 46.9 s（45.6 / 47.6） | 84 |

觀察：

- **耗時貼近理論最短值，且非常穩定**：Path 2 每批 2,977 筆三次都是 5.6 秒，比理論最短只多 0.2 秒。
- **Path 1 偶爾多 2 秒**（例如 2977 的 5.6 → 7.7 秒、1000 的 12.9 → 14.8 秒），差距恰好等於一次接收逾時，對應**最後一批被 Proxy1 丟棄**的情況：Client 要等逾時才發現，要求重傳後還要再等一次逾時才結束。
- **Path 1 重傳要求次數約等於被丟棄的批數**（例如 250 筆 × 400 批 × 30% ≈ 120 批，連續缺口合併後約 84 次），不再出現 64 KB 時數百到數千次的重傳風暴。
- **超過上限（2,978、3,000 筆）也從 22 ~ 34 秒降到 7 ~ 9 秒**：29 批送不出去（傳送失敗封包 86,362 / 87,000 筆），但緩衝區夠大，一次湧入的數萬個重傳封包都能被接收，只需 2 ~ 3 次重傳要求就補齊。不過仍比 2,977 筆慢，且完全依賴重傳，不建議使用。

> 指標修正：本次結果的初版把「Server 傳送失敗」的封包也算進「作業系統掉包」。`Q4.py` 已新增「傳送失敗封包」輸出，`run_batch_sweep.py` 計算作業系統掉包時會扣除這部分。本次結果已依「傳送失敗封包 = 傳送失敗次數 × 每批筆數」修正（失敗的都是完整批次，並已以 `--group=3000` 實測驗證為 29 × 3000 = 87,000）。

### 8.7 結論

| 目標 | 建議 | 實測 |
| :--- | :--- | :--- |
| **最快且穩定** | Path 2、每批 2,977 筆、`--rcvbuf=1048576` | **5.6 秒**（3 次皆同），無作業系統掉包；原本每批 10 筆推算約需 1,000 秒（未實測） |
| **有掉包路徑時最快** | Path 1、每批 2,500 ~ 2,977 筆、`--rcvbuf=1048576` | 約 6.3 秒；最後一批被丟時多 2 秒 |
| **不改緩衝區時最穩定** | 每批 250 ~ 500 筆 | 約 24 ~ 46 秒，無作業系統掉包 |
| **避免** | 超過 2,977 筆 | 大部分批次送不出去，完全靠重傳補回 |

- 在 `0.1s` 傳送間隔下，總耗時幾乎只取決於**傳送次數**。Proxy1 的 30% 掉包影響不大，因為重傳直接送回 Client，不經過 Proxy 也不受傳送間隔限制。
- 加大接收緩衝區後，**批次大小可以直接用到上限 2,977 筆**，不必再為了避免作業系統掉包而縮小批次。
- 剩下的約 2 秒是結尾的接收逾時；若要再更快，需要讓 Server 通知傳送結束，或縮短傳送間隔。

## 9. 已知限制

- **重傳直接由 Server 送往 Client**，不經過 Proxy，因此不會被 Proxy1 模擬丟棄。若要模擬重傳也可能掉包，需改為經由 Proxy 傳送。
- **重傳一筆送一次**：大批次被丟棄時會瞬間送出數千個小封包，在預設 64 KB 緩衝區下會被作業系統丟棄（見 8.3、8.4），可用 `--rcvbuf` 加大緩衝區解決。
- **Proxy2 為單執行緒阻塞式延遲**：延遲期間後續封包會在 UDP 緩衝區排隊，因此一筆延遲會連帶拖慢後面的封包（Q3 的 Path 2 也有相同現象）；批次大時排隊的資料量會超過預設緩衝區（見 8.3、8.4）。
- **`--rcvbuf` 預設不啟用**，以保留原題在作業系統預設設定下的行為；大批次傳輸建議設為 `1048576`。
- **結尾固定多等 2 秒**：Client 無法得知 Server 已經送完，只能等待接收逾時，因此每次執行的耗時都包含約 2 秒的收尾時間。
