## 3. 修復前問題分析

1. **程式印出結果後無法結束**：`proxy1_thread`、`proxy2_thread` 為無窮迴圈且未設定 `daemon=True`。
2. **重傳流程整條不通**：
   - 第 242、247 行 `server_receive_thread` 被註解，Server 收不到 `REQUEST_RETRANSMISSION`。
   - Client 送出的重傳編號是 `client_last_sent_packet // 10`（**批次序號**），Server 卻當成**封包編號**處理。
   - Server 重傳的訊息以 `(重傳)` 結尾，Client 以 `int(received_data.split()[-1])` 解析時拋出 `ValueError`，接收迴圈被 `except Exception` 中斷。
3. **缺包判斷的預期編號固定 `+10`**（第 182 行）：
   - 單筆模式下每一筆封包都被誤判為缺包。
   - 批次模式下只要遺失一批，預期編號就永久錯位，後續每一批都被誤判為缺包。
4. **單筆模式缺少 Path 3**（第 56–68 行）：`server_send_single_data()` 未處理 `choice == "3"`，不會傳送任何封包，最後除以零崩潰。
5. **掉包統計單位不一致**：批次模式下 Proxy1 每丟棄一批（10 筆封包）只讓 `loss_buffer` 加 1，與單筆模式的單位不同，掉包率無法比較。
6. **路徑選擇次數只在批次 Path 3 統計**：其他組合一律顯示 `0 / 0`。
7. **比率計算未處理分母為 0**、**`stop_threads` 用法錯誤**（與 Q3 相同）。

## 4. 修復內容

### 4.1 重傳流程重新設計

```text
Client 收到封包 ──> 以 regex 解析訊息中所有封包編號（單筆、批次、重傳訊息皆適用）
   │
   ├─ 第一個編號 > 預期編號 ──> 中間有缺口 ──> REQUEST_RETRANSMISSION <起> <訖>
   │
   └─ 接收逾時 ──> 與 1 ~ num_packet 比對，仍有缺包（例如最後一批被丟棄）──> 要求重傳後繼續等待
                   連續 3 輪逾時都沒有收到新封包才放棄

Server 收到 REQUEST_RETRANSMISSION <起> <訖>
   └─ 只重傳已送出過的範圍，每筆標註 (重傳)，直接送回 Client（不經過會掉包的 Proxy）
```

### 4.2 修改清單

| 修改 | 對應問題 |
| :--- | :---: |
| Proxy、Server 接收端與傳送端執行緒設為 `daemon=True` | 1 |
| 啟用 `server_receive_thread`；重傳要求改為 `REQUEST_RETRANSMISSION <起始編號> <結束編號>`，連續缺包合併成區間 | 2 |
| 新增 `parse_packet_numbers()`，以 `re.findall(r"server (\d+)")` 解析編號，可處理 `(重傳)` 標記 | 2 |
| Client 改用「下一個預期編號 + 已收到編號集合」判斷缺口，不再假設固定步進 `+10` | 3 |
| 抽出 `choose_proxy()`，單筆與批次模式共用 Path 3 的分流規則 | 4 |
| Proxy1 / Proxy2 改以**封包數**統計遺失與延遲，另外記錄被丟棄 / 延遲的傳送次數 | 5 |
| 所有路徑與模式都統計 Path 1 / Path 2 的使用次數 | 6 |
| 新增 `safe_percent()`；移除 `stop_threads`，接收迴圈改以逾時結束 | 7 |
| 新增輸出：重傳要求次數、重傳補回封包、最終收到封包、最終缺少封包 | 可觀察性 |
| 支援命令列參數 `python Q4.py [path] [mode]`，並檢查無效輸入 | 測試便利性 |

### 4.3 統計欄位定義

| 欄位 | 定義 |
| :--- | :--- |
| 掉包率 | Proxy1 丟棄的封包數 ÷ 總封包數 × 100 |
| 封包延遲率 | Proxy2 延遲的封包數 ÷ 首次傳送就收到的封包數 × 100 |
| 封包接收（首次傳送） | 不含重傳，第一次傳送就送達 Client 的封包數 |
| 最終收到封包 | 包含重傳補回，Client 收到的不重複封包數 |

### 5.2 重傳壓力測試

另外複製一份程式、將 `LOSS_RATE` 改為 `1.0`（Proxy1 丟棄所有封包），驗證「Client 完全收不到首次傳送、只能靠逾時重傳」的情境：

| 封包數 | 模式 | 重傳要求 | 重傳補回 | 最終收到 |
| :---: | :--- | :---: | :---: | :---: |
| 50 | 單筆 | 3 | 50 | **50 / 50** ✅ |
| 50 | 批次 | 1 | 50 | **50 / 50** ✅ |
| 200 | 單筆 | 11 | 200 | **200 / 200** ✅ |
| 200 | 批次 | 2 | 200 | **200 / 200** ✅ |

200 筆單筆模式的傳送時間約 20 秒，遠超過「3 輪 × 2 秒逾時」。修復過程中發現若重傳輪數不重置，Client 會在 Server 送完前就放棄；已改為**每收到新封包就重置輪數**，此測試確認修正有效。

## 7. 已知限制

- **重傳直接由 Server 送往 Client**，不經過 Proxy，因此重傳本身不會遺失。若要模擬重傳也可能掉包，需改為經由 Proxy 傳送，並處理重傳封包再次遺失的情況。
- **Proxy2 為單執行緒阻塞式延遲**：延遲期間後續封包會在 UDP 緩衝區排隊，因此一筆延遲會連帶拖慢後面的封包（Q3 的 Path 2 也有相同現象）。
