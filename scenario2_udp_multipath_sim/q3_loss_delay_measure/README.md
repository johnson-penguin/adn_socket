# Q3：單筆傳輸的掉包率與延遲率量測

> **狀態：已修復並驗證**。第 2、3 節為修復前的原始實測與問題分析（行號對應修復前版本）；第 4、5 節為修復內容與修復後驗證結果。
> 共用拓撲與埠號請見[情境二總覽](../README.md)。

## 1. 參數設定

| 參數 | 值 |
| :--- | :--- |
| 封包數 | 預設 `1000` 筆，可由第 2 個命令列參數指定（本報告實測使用 `100` 筆） |

| **Path 3**（`Client → Server`） | 直接傳送，不經過 Proxy |

> **1,000 筆耗時推算**：Path 1 約 `1000 × 0.1s + 5s ≈ 105s`。Path 2 因 `proxy2_receive_and_send` 為單執行緒阻塞式 `time.sleep(0.5)`，平均每筆在 Proxy2 消耗 `0.25s`（大於傳送間隔 `0.1s`），封包在 UDP 接收緩衝區排隊，總耗時約 `500 × 0.5s + 5s ≈ 255s`。

## 3. 修復前問題分析

1. **程式印出結果後無法結束**：`proxy1_thread`、`proxy2_thread` 內為 `while True:` 無窮迴圈，且未設定 `daemon=True`，主程式結束後仍卡在 `recvfrom()`。
2. **Path 3 沒有傳送任何封包**：第 147、154 行 `client_send_thread` 被註解，選擇 Path 3 時 5 秒後 `receive_buffer`、`loss_buffer` 皆為 `0`，第 165 行除以零崩潰。此外 Path 3 由 Server 接收，但統計使用的是 Client 端的 `receive_buffer`，即使傳送也不會被計入。
3. **比率計算未處理分母為 0**：收到 0 筆封包時，掉包率與延遲率計算都會觸發 `ZeroDivisionError`。
4. **`stop_threads` 用法錯誤**：先宣告為 `threading.Event()`，後又被覆寫為 `False`，`while not stop_threads` 只是剛好可運作，Event 實際上沒有作用。

## 4. 修復內容

| 修改 | 對應問題 |
| :--- | :---: |
| Proxy 與傳送端執行緒設為 `daemon=True`，主程式只等待傳送端完成與接收端逾時 | 1 |
| Path 3 啟動 `client_send_data`，`server_receive_data` 改為 5 秒逾時結束並計入 `receive_buffer` | 2 |
| 新增 `safe_ratio()`，分母為 0 時回傳 `0.0` | 3 |
| 移除 `stop_threads`，接收迴圈改以逾時結束 | 4 |
| 新增 `sent_buffer` 統計實際送出數；掉包率、延遲率等參數改為檔案開頭的常數 | 可讀性 |
| 支援命令列參數 `python Q3.py [path] [num_transmissions]`，並檢查無效的路徑輸入 | 測試便利性 |
